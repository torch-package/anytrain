# 全仓分析（2026-09-18）

分析基线：`1befbfa`，已推送 `origin/main`。本报告以该提交的独立源码快照为准，
不包含工作区同时开发的 GLM4 intermediate features、feature shards 及其文档/测试。
这是一轮分析；下列新发现没有在本轮顺手修改。

## 结论

已有重构改善了依赖方向和状态所有权，无需再做全仓目录或 API 迁移。
当前优先级应从拆文件转到 **数值 dtype、mask 隔离和异步取消**：补充实验确认了五类行为问题，
其中三个会令合法训练输入得到 NaN/零损失，或令程序关闭卡住。现有测试全绿并不覆盖这些边界。

| 优先级 | 编号 | 问题 | 实测结果 |
| --- | --- | --- | --- |
| P1 | R1 | GRPO advantage 的 epsilon 跟随 reward dtype | FP16 等奖励得到 NaN；整数 reward 同样无法正常使用 |
| P1 | R2 | masked reduction 在 FP16 累计分子/计数 | 65,536 项均值得到 NaN；flow/frame MSE 应为 0.25 却得到 0 |
| P1 | R3 | Chat 等锁任务在 event-loop shutdown 时被共同取消 | 本应很快退出的子进程超过 5 秒仍未退出 |
| P2 | R4 | weighted Metric 以低精度浮点累计整数计数 | 257 个 BF16 的 1 计为 256，均值变成 1.0039 |
| P2 | R5 | stream broadcast 通过乘零屏蔽 padding | 有效值 3 加 NaN padding，传播成两个 NaN |

P1 指建议优先修复的训练/退出行为问题，不代表所有调用都会触发。
这些问题按当前完整版本报告，不将它们一概归因于本轮重构；例如 Chat 等锁循环原本就存在。

## 已确认问题

### R1 — FP16 等奖励的 GRPO 会产生 NaN

位置：`src/anytrain/framework/rl/advantage.py:35–44`；调用链包括 token、continuous 和 neighbor GRPO。

`group_relative_advantages()` 把默认 `eps=1e-8` 构造成 `rewards.new_tensor(eps)`。
FP16 中该值下溢为零；同组 reward 全相等时，centered 和 std 都为零，最终变成 `0 / 0`。
用 FP16 `[[1, 1]]` 即可复现，不需要极端规模或非有限输入。完整 `GRPOLoss` 同样返回 NaN。
FP32 对照结果为零。

验证还发现整数 reward 通过了当前 real-valued 校验，但 epsilon 截断为零；完整 GRPO 又在
诊断 `mean()` 遇到 Long dtype 报错。因此 reward 的接受范围与数学实现没有一致。

建议：归一化在至少 FP32 的计算 dtype 进行，保留 FP64 输入精度；对整数 reward 明确采用
转换或拒绝策略，诊断统计使用相同策略。回归覆盖 FP16/BF16/FP32、等奖励、候选 mask、
整数奖励以及完整 loss 的有限梯度，不能只验证 advantage 的 shape。

### R2 — FP16 masked reduction 的计数溢出会静默改变训练目标

位置：`framework/rl/logprob.py:40–62`、`framework/flow_matching/objective.py:44–54`、
`loss/frame.py:255–258`（均相对 `src/anytrain/`）。

这些路径把 mask/count 转成 value/prediction dtype，再求和或乘 feature width。
FP16 最大有限值为 65,504，65,536 个元素已足以溢出。实测：

| 入口 | 输入 | 应得 | 实得 |
| --- | --- | --- | --- |
| `masked_mean` | 65,536 个 FP16 的 1，全选 | 1 | NaN |
| `sequence_logps(..., reduction="mean")` | 一行 65,536 个 FP16 的 -1 | -1 | NaN |
| `masked_mse_velocity_loss` | `[1,256,256]`，prediction=0.5 FP16，target=0 FP32 | 0.25 | 0 |
| `masked_frame_mse_loss` | `[1,65536,1]`，prediction=0.5、target=0，FP16 | 0.25 | 0 |

flow 例子甚至不需要 65K 帧：256 帧乘 256 维就使 denominator 溢出。
零损失比显式异常更容易被训练日志漏掉。此前修复的 NaN padding 隔离仍然正确，但不足以
保证累积 dtype 的稳定性。

建议：计数使用整数或足够宽的 dtype；分子及平方等中间运算使用至少 FP32，再按明确契约
决定返回 dtype。扩展检查到 GRPO 的各 reduction 和 stream pooling，避免只修一处 helper。
保留不同目标的 token/sequence/frame 分母语义，不统一成一个过度泛化的 loss 抽象。

### R3 — Chat 在 asyncio.run 关闭阶段可能无限等待

位置：`src/anytrain/chat/chat.py:398–412`。

`_async_text_lock()` 对 acquire task 使用 shield，并在捕获 `CancelledError` 后继续等待。
这能处理仅外层请求被取消的情况；但 `asyncio.run()` 退出时会取消所有剩余 task，内部
acquire task 也会直接被取消。对一个已经 cancelled 的 task 再次 shield，会立即抛出相同
异常，循环无法结束。

复现没有外部请求：锁先被占用，启动一个等待 `_async_text_lock()` 的 task，main 返回；
另一个线程在 0.2 秒后释放锁。程序仍在 5 秒后被父进程超时终止。

现有测试覆盖外层任务的重复取消，以及 SDK cleanup/request 的取消，但没有覆盖
**内部 acquire task 也被取消** 的 event-loop shutdown 场景。

建议：区分外层取消和 acquire 自身取消，并处理 `to_thread` 被取消后底层线程仍可能成功
取得锁的情况。需要同时证明退出有界与锁没有遗留，不能只加一个 break。
回归使用隔离子进程，避免缺陷把整个测试 runner 卡住。

### R4 — weighted Metric 的精确 count 被低精度求和破坏

位置：`src/anytrain/evaluator/weighted.py:15–28`。

权重逐项校验 finite、non-negative、integral 后，却直接 `weights.sum()`，仍在原 dtype
累计。257 个 BF16 的 1 被舍入成 256；分子在 `_mean()` 已提升 FP32，所以结果变成
`(1.00390625, 256)`，而非 `(1, 257)`。65,536 个 FP16 的 1 则在转 int 时触发 OverflowError。

这个 count 还会进入 Lightning 的 count-weighted 聚合，影响跨 batch/rank 的均值权重。
建议验证后在能精确表示合法 count 的 dtype 求和，并定义最大支持范围；为共享 weights
的 count cache 和分布式聚合补低精度权重测试。不要把 metrics 的整数计数契约改成近似权重。

### R5 — stream broadcast 的 padding 可污染有效输出

位置：`src/anytrain/module/stream/materialization.py:295–298`。

BROADCAST 的 `source.values * valid` 不能屏蔽 NaN/Inf。构造合法 `Features`：值为
`[[[3], [NaN]]]`、length=1，再 broadcast 到长度 2 的零 carrier，得到 `[NaN, NaN]`；
有效位置应只由 3 决定。当前 Features 校验不禁止 padding 的非有限值。

建议在求和前用 `masked_fill`/等价选择屏蔽无效 source；同时审查 target mask、LINEAR
零权重分支和空 source 行。已确认的复现是 BROADCAST，不将其余分支未经验证地判为同一 bug。
回归需要比较有效输出及梯度，不只检查 padding 输出是否为零。

## 架构与维护成本

依赖方向已明显改善：显式非 Lightning 模块中的 Lightning 导入集中在 S2S integration；
embedding、ADT、quantization、text、COMET、S2S 的 import-isolation 子进程测试全部通过。
该观察不等于已经动态检查每一种 optional import 组合。

仍然较大的代码主要是状态机：observation callback 1,547 行、state 1,238 行，checkpoint
storage 1,036 行、callback 964 行，unit schedule callback 842 行。它们不是自动的重构清单。
`_chinese.py` 的 2,090 行大部分为静态映射，更不应被当作复杂度热点。

真正需要集中审阅的是跨阶段路径：checkpoint last 发布与错误恢复、observation
collective 前后的验证、manual optimizer step 时钟，以及 SDK 取消后线程仍运行的情况。
应以具体状态转换和回归用例降低维护成本，避免再增加只有转发作用的 facade。

## 建议顺序

1. 分别修 R1、R2、R3，每项有独立行为回归；数值修复明确 FP32/FP64 保留策略，取消修复
   验证进程退出和资源回收，不顺便替换整个 Chat 锁模型。
2. 修 R4、R5，并将 low-precision count / masked non-finite padding 作为跨模块检查维度。
3. 固定 CI 基线：本提交未找到受版本控制的 `.github` workflow；建议先跑 CPU/Gloo、Ruff、
   类型检查，再为可选依赖建立少量代表性隔离环境。这里是仓库内证据，不排除外部已有 CI。
4. 单独定位 UniCodec 在快照中的类型解析差异，避免用工作区“0 errors”代替可复制验收。
5. 按 todo 继续真实 8-rank stall audit、DAC 权重 smoke 和可选 backend 环境验证。
   只有新需求使边界变差时，再做 BiCodec/TTS/translation 等条件性拆分。

当前工作区的 GLM4/features/shards 是另一批并行开发，不作为本提交的已验证能力，
