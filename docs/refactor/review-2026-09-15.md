## 已确认的行为问题

以下均为 P2：应在正常修复周期处理。结构建议的排序另列，不能把文件长直接视为运行缺陷。

### B1. 后台 cost producer 在退出竞态中可能永久等待

位置：[cost.py:133](../../src/anytrain/cost.py:133)，关键阻塞点为第 147 行。

触发顺序：worker 正在计算，队列已满；另一线程进入 `close()`，通过一次 `check()` 后阻塞于 `queue.put(None)`；此时计算抛异常，worker 退出，不再消费队列。默认 `timeout=None`，关闭线程因此没有唤醒来源。上下文管理器退出也会调用这个路径。

最小复现使用容量 1 的队列、两个 index 和 Event 控制计算失败时机，观察到 `worker_alive=False`、`close_stuck=True`、队列仍满；手动腾出队列位置后，close 才抛出原有 worker failure。

建议把终止状态、worker 健康检查与有界等待统一由一个生命周期实现拥有。停止信号可采用独立 Event 或短超时入队循环；失败后仍需完成资源收尾，再传播异常。仅在阻塞前增加一次检查不能消除竞态。回归测试应覆盖满队列退出期间 worker 失败。

### B2. FLOPs helper 破坏混合 train/eval 状态

位置：[profile.py:26](../../src/anytrain/lightning/perf/profile.py:26)。

`profile_forward_flops()` 只保存根模块的 `training`，恢复时递归执行 `module.train(was_training)`。当父模型处于训练模式，但某个冻结 teacher、BatchNorm 或 Dropout 被独立设为 eval 时，测量结束会把它重新置为 train。

复现：`Sequential(Linear, Dropout)`，父模块 train、Dropout eval；测量前模式为 `[True, True, False]`，测量后变为 `[True, True, True]`。这会改变后续训练的 Dropout/BatchNorm 行为。

建议保存并恢复每个子模块的状态，覆盖成功与异常路径。仓库的 `s2s.condition.ConditionGainCallback` 已有逐模块恢复的做法；可以先复用这一明确语义，不必为此引入大型运行时抽象。

### B3. ASR semantic config 丢失 text metric profile

位置：[asr.py:51](../../src/anytrain/evaluator/speech/asr.py:51)、[_config.py:51](../../src/anytrain/evaluator/speech/_config.py:51)。

`TextComparisonEvaluator` 支持 `bleu_tokenize`、`chrf_word_order`，但 `WhisperASREvaluator` 构造 semantic config 时只复制 normalization 和 bleu_smoothing。两个不同评分定义具有相同 semantic ID，且 `semantic_config.evaluator()` 重建时退回默认 profile。

已复现：`chrf_word_order=0` 与 `2` 比较 `hello world` / `hello worlds`，得到约 89.9322 和 73.7138，但 ASR semantic ID 相同；后者配置重建后的 word order 为 0。依赖该 ID 识别评分语义的下游无法区分它们。

建议由 text 模块拥有完整、可序列化的 metric profile，speech 持有并转发它，避免在两层分别枚举字段。保留旧身份兼容策略需显式决定。补 profile 差异身份测试和配置往返测试。

### B4. 部分 framework mask helper 不能隔离无效位置的非有限值

位置：[flow_matching/objective.py:44](../../src/anytrain/framework/flow_matching/objective.py:44)、[rl/logprob.py:40](../../src/anytrain/framework/rl/logprob.py:40)。

flow masked MSE 在平方后乘零 mask；`sequence_logps` 和 `masked_mean` 同样直接乘零。`NaN * 0`、`Inf * 0` 仍是 NaN，padding 或未选择位置的非有限值会污染有效项。

已复现：`sequence_logps([[-1, -inf]], [[True, False]])` 返回 NaN；flow prediction 为 `[[[1], [NaN]]]`、target 全零、mask 为 `[[True, False]]` 时，loss 为 NaN，屏蔽位置梯度也是 NaN，预期有效 loss 为 1。

建议在不安全算术前用 mask 选择有效项或清零输入，确保屏蔽位置梯度为零。flow 的平方必须在屏蔽之后；仅对最终 loss 执行 `nan_to_num` 会掩盖有效位置的错误。`loss.frame` 和 GRPO 主实现已有先屏蔽输入的做法，可统一边界语义，但不应强行统一 token/sequence/trajectory 的不同分母。

## 逐模块分析

### 1. package root、stats、env、utils、cost

判断：轻量根包和显式组件入口合理，保留。

`anytrain.__init__` 只有空公开命名空间；`stats.py` 只做 tensor 聚合，`utils.py` 保持少量 tensor 工具，`env.py` 只处理 cache root，职责清楚。`_audio.py` 是 audio、speech、example 的共享 waveform helper，没有在根包自动加载。

`cost.py` 只拥有 bounded background computation，不解释 dataset schema，放在库内有实际复用意义。应优先修 B1；无需现在把它与进程物化、长驻服务合成一个泛化 worker 框架。

共享能力目前有两个值得收拢的方向：canonical serialization 的位置，以及少量已经发生行为分歧的 mask/状态恢复规则。各种正整数 validator 仅因相似而出现，并不足以新增全仓统一 validation 框架。

### 2. observation

判断：声明层与 Lightning transport 分离合理，保留三个文件的基本结构。

`types.py` 拥有值、source 和 reduction 契约；`_binding.py` 拥有 concrete-type registry、context、event、claim/release；`__init__` 提供公开入口。底层没有导入 Lightning，module/loss 的观察中间量也不侵入 forward 返回值。

精确 concrete-type 注册和一次性推荐提示是已明确选择的语义，不能随意改为沿继承链搜索。`BackwardObservation` 是明确记录的未实现占位，不把它当本轮新缺陷。

改进重点在 transport 内部：下一节建议先让状态及其 schema 有独立内部 owner，同时保留 `_binding` 的私有 SPI 定位。

### 3. lightning 入口、logging、experiment、debug、parameter policy

判断：按需加入 callback 的使用方式合理；根入口的 eager re-export 放大了底层反向依赖。

`mixin.log` 负责训练模块侧便利调用；`experiment` 负责 writer capability；`_capability` 负责 Trainer/strategy 能力检查；debug 和 parameter policy 各自拥有明确行为。无需合并成大基类。

`lightning.__init__` 会加载完整 callback 集合。正常 Lightning 用户可以接受，但 `module.embedding` 只为 canonical hash 导入 checkpoint，实际也加载了全部 37 个 `anytrain.lightning*` 模块，包括大体积 checkpoint/observation callback。这是可观察到的依赖扩散，不只是目录命名偏好。

建议优先下沉共享 primitive，再考虑根入口是否需要惰性导出。只换成 `lightning.checkpoint.contract` 导入无法跳过父包 `__init__`，不能解决根因。

### 4. lightning.audit

判断：功能有明确下游需求，但职责放置需要调整，列为结构优先项。

1,292 行同时包含 JSONL bounded sink、文件锁/持久化、进程环境/context、collective/operation tracing 和 TrainingAuditCallback。普通量化器、ADT、text/COMET evaluator 为记录 collective 导入此 Lightning 模块。

建议形成不依赖 Lightning 的内部 audit runtime，拥有 sink、context、事件和 collective wrapper；Lightning adapter 只解释 hook、step 与 Trainer 信息。保持现有公开路径兼容。原有 `_retain/_release/_use_audit_sink` 也应继续有单一 owner，避免 checkpoint 维护第二套 sink 生命周期。

不要把 JSONL schema、事件顺序与 callback 拆分混在一次行为改动里；既有审计测试可用于固定兼容性。

### 5. lightning.callback.checkpoint

判断：单一类承担的职责过多，建议渐进提取，不能只按行数切文件。

`ModelCheckpoint` 占据约 1,868 行类体，既处理 Lightning top-k/last/unit trigger，又拥有临时文件、线程池、pending futures、发布顺序、deferred removal、audit 和跨 rank 错误同步。

合理切分点是独立资源与状态 owner：

- callback 保留保存触发、Lightning 状态和 rank 协调。
- storage 内部对象拥有 executor、pending job、backpressure、复制/原子发布及关闭。
- 每个保存 job 用一个记录绑定 future、源/目标、audit、完成回调；减少多张按 future/path 索引的字典之间的一致性要求。

提取前固定 top-k/last 的可见顺序、删除时机、失败传播、pickle 与 teardown 契约。优先把完整状态连同操作一起移动，避免“工具函数反向读 callback 私有字段”的伪拆分。

### 6. lightning.checkpoint contract/loading/evaluation

判断：三种业务职责本身合理；canonical JSON primitive 不应由 Lightning 层独占。

`loading.py` 的显式路径、CPU load、module hook 和 strict state loading 顺序清楚。`evaluation.py` 是按步发现和显式 evaluate callback 的薄编排，没有接管 Trainer。`contract.py` 的 state-dict schema 仍可留在 checkpoint。

其中 `canonical_value/stable_json/canonical_sha256/first_difference` 可分为共享 contract primitive，供 embedding 与 checkpoint 共同依赖。与 `_semantic.py` 的合并必须谨慎：两者对 Unicode、Enum、dtype、set、key 的处理不同，已有 digest 不能静默变化。可以共享底层实现并保留明确版本/profile，而不是替换所有 hash。

### 7. lightning.callback.observation

判断：逻辑上已有分区，文件内仍缺独立状态 owner，是第二个结构优先项。

2,858 行包含 histogram/profile/curve/heatmap 状态，hook/event 收集，train/validation cadence，分布式预检/归约，writer 输出和 checkpoint 编解码。既有 readability 文档正确指出这些逻辑共享不变量，不能为缩短文件盲拆。

本轮建议以完整职责拆：状态、delta、schema、snapshot、checkpoint 编解码一起进入内部 state 模块；writer 消费稳定 snapshot；callback 只负责挂接、阶段推进、同步和调用 writer。分布式 schema 检查与状态的关系必须显式保留。

这样能单独测试 histogram/EMA 数学、checkpoint 往返和 writer capability，也能减少状态变更对 1,286 行 callback 类体的影响。当前无证据要求改公开 observation 类型或 callback 参数。

### 8. lightning.schedule 与 optim.scheduler

判断：schedule 内部的 curve/data/spec/runtime/callback 拆分合理；两套 LR 曲线计算存在维护重复。

`optim.scheduler` 提供 constant/warmup_cosine/wsd 的纯 Torch helper；`lightning.schedule` 提供显式分段曲线和 step/unit runtime。两种入口对用户都成立，不建议删除其中一个。

若后续调整曲线，优先让它们共享纯数学定义或数值一致性测试；不能让 optim 反过来导入整个 Lightning 包。unit callback 虽达 842 行，但其核心是同一个时钟状态机，暂不列为优先拆分类。

保留 unit provider 的显式注入、checkpoint fingerprint 与 stop budget 的区分，以及按 optimizer step 处理 accumulation 的约定。

### 9. lightning.perf、performance callback、auto_cost

判断：估算、观测和校准三种能力总体边界清楚。

`perf.hardware/profile/metrics` 分别负责设备能力、代表性 forward 和计算口径；PerformanceCallback 将它们接入训练窗口；auto_cost 通过 hooks 让下游解释 batch，避免将 token/audio 语义带入 core。

先修 B2。auto_cost 的纯拟合与 CUDA probe 可以在再次扩展时分开，但目前 467 行并不构成强制重构理由。FLOPs profiler 的算子覆盖不等于真实 GPU 性能验收，当前测试不能替代 CUDA/NCCL 测量。

### 10. lightning.materialization、service、oom

判断：三者目标不同，应保留独立入口；抽取已重复的协调 primitive。

materialization 是一次发布并在各 rank 加载；service 是长驻服务健康与退出；oom 是诊断上下文和报告。把它们统一成通用 callback 基类会增加状态组合。

`materialization.py:444` 和 `service.py:305` 附近的 `_sync_rank_errors/_sync_active_state/_rank_world/_global_rank` 明显重复。应由一个内部 rank-coordination 模块拥有协议、payload 校验和统一错误选择，两个 callback 仍拥有各自生命周期。

### 11. lightning.loss/grad/ema/validation

判断：按观察对象拆分合理，保留。

LossSummaryCallback 汇总显式 scalar 输出；GradientProbeLoggerCallback 计算目标/probe 梯度关系；EMA 管理参数影子与交换；validation 拥有计数加权日志、History 和 unit epoch interval。它们没有合适的共同业务抽象。

`evaluator.weighted.Metric` 的分子/计数边界对分布式平均很有价值，本轮 count 非整除 world-size 的真实测试通过。无需用“统一 metric 平均器”替代 corpus BLEU/COMET 或这些不同归约定义。

### 12. loss

判断：本轮拆分较合理，保持 scalar-only 和 observation 分离。

| 子模块 | 判断与建议 |
| --- | --- |
| abc/group | scalar 校验、子 loss 调用与组合边界清楚；不增加 batch 路由或任务解释。 |

### 14. optim

判断：ParameterPlan 作为共享分组 owner 很好，整体保留。

`_params/rules` 统一遍历和策略；adamw/muon 负责实例化；CompositeOptimizer 拥有多个 optimizer 的组合与恢复；lora_muon 负责低秩算法，peft 仅负责外部 adapter 提取。算法和模型集成边界清楚。

`llm.py` 与 `peft.py` 的 PEFT Linear/FSDP 识别有重复，可抽成小型可选适配 helper；不让普通 AdamW import 强制依赖 peft。当前 peft 有两个类型收窄诊断，优先修真实检查。scheduler 的重用问题见第 8 项。

### 15. module 根、ADT、DiT

判断：模块不解释 batch/task，定位正确。

ADT 拥有温度适配与统计，DiT 拥有条件表示、attention/block 和主网络。较长实现本身不是跨领域混杂；不要把每个 math helper 单独拆文件。

ADT 的 collective audit 应改依赖第 4 项的底层 audit primitive。DiT 若继续增长，可按 condition state 与 attention/block 的完整职责拆；目前先保持公开积木 API 和 eager/SDPA 行为测试。

### 16. module.moe 与 moe.conv

判断：partition → route → execute → restore 的主流程清楚；bank 的执行选择集中度偏高。

| 子模块 | 判断与建议 |
| --- | --- |
| routing / metrics / loss | 路由表示、诊断、aux loss 分离合理；不要隐式向训练 loss 加 aux 项。 |
| layer | 负责组装和调用次序合理。 |
| expert / params / expand / grid | 算子说明、参数扩展、绑定和布局描述有不同职责，保留。 |
| bank | 836 行内分支处理 Linear/Conv1d/Transpose/Conv2d/generic；后续可将具体执行器按 family 提取，bank 保留参数所有权。 |
| sparse | 独立 nn.Module experts 分发需保留 forward/parameter hooks 与未使用参数 `grad is None` 语义。不能直接并入参数 bank 路径。 |
| conv | shape、segment、partitioner、router、grouped kernels 已按可复用运算拆分；保留。 |

bank 与 sparse 的 route 内存预算计算和 host index 搬运有重复；只共享无状态计算，避免为减少重复破坏两个执行路径不同的参数/梯度语义。

### 17. module.quantization

判断：按量化算法拆分合理，公共 runner/helper 已发挥作用。

| 子模块 | 判断与建议 |
| --- | --- |
| output/protocol/types | 统一结果和能力契约合理。 |
| finite_scalar | FSQ grid、index 转换和 projection 属于同一算法，不需要再切细。 |
| embedding | VQ 数学、kmeans 初始化、dead-code 回收、EMA 分布式状态集中；若扩展 EMA 策略，适合提取有完整状态的 EMA owner。 |
| grouped | 分组与 mixed-radix 转换复用 helper，合理。 |
| residual | runner 拥有 residual/dropout 循环，具体 VQ 负责阶段算法，合理。 |
| residual_finite_scalar | scale-space residual FSQ 与一般 RVQ 不完全相同，独立实现有理由，不能为统一而硬套 runner。 |
| auto_group_residual | AGRVQ 两层职责仍可辨认；优先保持 shared output/runner 契约。 |
| lookup/checks/product_codebook/projection/stats/observation | 搜索、校验、编码、投影、统计、声明均有清楚 owner，保留。 |

修复分布式 audit 依赖方向；保留空 rank 参与 EMA collective 的机制。该机制的真实 Gloo 测试本轮通过，不应在简化 dropout 循环时去掉。

### 18. module.token_space 与 embedding

判断：ID layout 和参数 owner/view 分离合理，embedding 有两处职责可以收紧。

token_space 121 行只做 local/global 区间映射，不拥有 tokenizer。EmbeddingBank 持有参数，EmbeddingView 作为非拥有方向视图，能避免重复 optimizer/checkpoint 路径，值得保留。

首先解决 canonical hash 引入整个 Lightning 包的问题。其次 `_owner_contract_state()` 自动识别 `fsq_levels/codebook_sizes/topology/level_values/config.feature`，让通用 owner 开始承载特定量化 family 的结构知识。可以逐步改为显式 metadata 或窄的 contract-state provider，并为 nn.Embedding 提供默认实现。无须新增完整 provider registry。

### 19. module.stream

判断：本轮最清楚的分层之一，建议作为后续重构参照。

expression 声明、layout 编译、binding 校验、materialization 执行、output target routing 和 types 分开；声明/布局不注册模型参数，Materializer 才拥有 embedders/operators。对齐与 local target ownership 也保持显式。

layout 中逐样本编译以及执行中的 `bool(tensor.any())` 会影响 accelerator hot path，但没有 benchmark 证据前不报性能回归。后续优化应通过编译计划复用或已校验输入路径进行，不能把布局和模型执行重新揉成一个类。

### 20. module.qwen

判断：builder 与 experimental predictor 分开合理。

qwen3.py 延迟导入 Transformers，兼容点集中；mtp.py 使用该 builder 组合 temporal/MTP 预测。保留 experimental 定位，KV cache 和具体 codec 训练语义继续由明确需求驱动。

mtp 的训练与自回归生成可以在下一次复杂度增长时形成独立内部路径；目前没有理由把两文件再拆成大量 facade。

### 21. audio 方向协议与 codec 公共层

判断：waveform 方向接口、静态 metadata、backend loader/cache 分离合理。

`_tokenizer/_detokenizer` 拥有方向 ABC，公开子包转发；codec 的 spec/capability/planning/registry 分别服务描述、能力查询、预算估计与延迟加载。`_registry.py` 是 entry 数据类型，`registry.py` 是运行逻辑，属于有意义的区别。

后续可将方向 ABC 的实现放在对应公开子包内部以降低跳转，但收益低，不作为优先任务。当前 backend cache 有锁且 loader 与 metadata 分开，避免重复模型加载的设计应保留。不要为双向 convenience 再引入一个包含所有能力的巨大 AudioCodec 基类。

### 22. audio.codec 各 backend

| Backend | 单独判断 |
| --- | --- |
| DAC | assets、registry、codec 三层简洁；真实 checkpoint smoke 尚在 todo，不把 fake 测试当权重兼容保证。 |
| UniCodec | loader/assets 与算法包装分开；现有 Python 3.12 上游支持限制应继续显式记录。 |
| Stable Codec | 单 backend 包装和 frame 表示合理；保留不支持组合的明确报错。 |
| GLM4 | source/runtime 加载、依赖指导与 online encode 混在 509 行文件内；可先将 upstream source/loading 提成内部模块。 |
| BiCodec | 734 行同时拥有 wav2vec2 特征、semantic/global 两条路径、padded length 传播和 backend 加载。适合按 frontend、length planning、backend loading 提取，避免改变联合 protocol。 |
| LongCat | 779 行包装中已有 assets/tokenizer/detokenizer；底部环境修改和专用 debug trace 是额外职责，优先提取 trace 与加载上下文。trace 的 CUDA peak reset 应明确影响测量口径。 |

BiCodec/LongCat detokenizer 有相似 feature routing，但 semantic stream 仍可能有差异；先固定公共行为再提取，不直接合并整个 backend。

### 23. audio.bpe

判断：代码序列 BPE 与神经 codec 隔离正确。

api 负责 facade/序列化，FrameCodec 负责 frame-ID 编码，CoreBPE 负责词表与 merge，trainer 负责可复现配置，eval 负责统计，deps 负责 optional 导入，基本合理。

`_core.py` 还拥有 tqdm/progress、corpus 扫描和训练调用。若继续扩展，训练执行可移至内部 training 模块，保留纯 core 数据结构；不要把 backend 训练逻辑硬塞进只有 73 行的公开 trainer spec 文件。

### 24. tts 公共层与各 backend

判断：协议和引擎环境隔离合理；adapter 之间的请求规范化重复较多。

| 子模块 | 单独判断 |
| --- | --- |
| protocol | reference、voice/engine capability、options、output、backend 协议均属于公共边界，448 行可接受；只有增量扩展时才考虑拆 types/options。 |
| environments | 明确不同 engine 的互斥版本契约，很有必要；不应追求一个包含所有 TTS extras 的环境。 |
| _omni | MOSS/Qwen 共享 generate/chunk/order/sample-rate 处理，提取位置正确。 |
| MOSS | config/deps/loading/runtime/output/omni 已有细分，是其它大型 adapter 的可参考结构；别继续只按长度细切。 |
| Qwen | prompt estimator 与 Omni prompt 已分开；551 行 tts.py 仍包含 config/loading/request/output，可先提 loading/output。 |
| CosyVoice | 666 行同时兼容 legacy flags、多版本、多声线模式、并发、reference materialization；优先将 legacy config normalization 和参考音频物化从核心合成流程分离。 |
| Spark | 422 行规模尚可，但 reference alias、临时音频文件处理与 MOSS/CosyVoice 重复；优先共享这一确定职责。 |

`_common.hashable_value()` 对任意对象退回 `str(value)`，而 `_semantic` 使用严格 JSON 值域。这两套 hash 契约不应静默合并，需明确何者用于持久身份、何者仅作辅助记录。

### 25. translation

判断：protocol 轻量，dataset-independent 边界正确；qwen.py 职责略集中。

position-aligned 字符串批协议不选择 dataset row；QwenTranslationSpec、load options、factory、token estimator、runtime、prompt 同在 539 行文件。语义配置与物理加载选项分离值得保留。

若继续扩展，按 spec、prompt/planning、backend loading/runtime 切三块最自然；只有一个 backend 时不增加通用 registry。prompt 与 token estimator 必须共享生成规则，防止预算估计和实际请求再次漂移。

### 26. chat

判断：request/response/config/client/OpenRouter 分拆基本合理，生命周期管理尚有补强空间。

Chat 拥有会话历史和锁，request 负责 provider 参数与日志，response 负责提取结果，OpenRouter 拥有目录解析，边界可理解。`_provider.py` 只是私有转发 facade，不宜继续添加业务逻辑。

Chat 同时持有同步、异步客户端，却没有公开 close/aclose 或 context-manager；可在确认 SDK 生命周期契约后补显式释放，以利于短生命周期批处理使用。这里是设计建议，本轮未复现连接泄漏。

异步锁用线程等待同步 Lock，取消处理较复杂，宜用明确的并发/取消测试保护；不应在目录整理中顺便更换锁策略。图像输入编码与图像生成两件事可各自保留清楚命名。

### 27. s2s

判断：模型侧领域契约有独立存在价值，data/model 与 callback 应更清楚地分开。

| 子模块 | 单独判断 |
| --- | --- |
| data | waveform/content/route 与 token training batch 两组契约共存，599 行；未来可按 semantic IO 与 token IO 拆开，继续不拥有 dataset collator。 |
| model | generator、token stepper、scorer 能力显式；483 行仍可读。LossStat 的 sum/count 避免不等长 batch 平均歧义，应保留。 |
| training | token objective/report 转换薄且显式，不接管 LightningModule，保留。 |
| condition | probe/result/bootstrap 数学与 ConditionGainCallback 同文件；637 行，建议把 callback 移至领域 integration 子模块。 |
| metrics | pure metrics/window 与 S2SMetricsCallback 混合，同样适合隔离。 |
| package root | eager 导出 callbacks，使只导入 data 也进入 Lightning 大依赖链；在保留公开兼容的前提下减少这种耦合。 |

这些领域 callback 留在 s2s 而不挪入通用 Lightning core，符合模块准入。拆分后应能单独使用数据/模型协议而不加载所有 callback。

### 28. framework.flow_matching、gan、rl

| 范式 | 单独判断 |
| --- | --- |
| flow_matching | source/time/path runtime/objective/sampler/stochastic 划分合理；修 B4。ODE 与 discrete solver 不应合并为掩盖不同参数语义的万能 sampler。 |
| GAN | criterion/feature/penalty/组合 Loss/manual steps 分工合理；discriminator、backward、optimizer 都显式，保持可组合。DAC preset 独立 audio 子包合理。 |
| RL | DPO/token GRPO/continuous GRPO/neighbor GRPO 分开合理；advantage/logprob/observation 有公共 owner。token/continuous 的 candidate-mask 校验和 reduction 结构重复，可先抽窄 helper。修 B4 时不要改变不同范式的归约分母。 |

framework 根包轻量，没有隐式训练入口。无需将范式 objective 统一继承 LossABC 才算“结构一致”；只要输入、scalar 返回和 observation 的契约清楚即可。

### 29. example、examples、scripts、tests、docs、packaging

判断：runnable examples 与 packaged fixture 分开合理，验证入口需要补足。

example/resources 用于定位资源，example/audio 用于解码，examples/tiny_regression 拥有可运行训练流程，scripts/summarize_audit 属于运维辅助。这些都没有进入训练 core。

测试已覆盖大量数值、恢复、fake backend 和真实 Gloo 边界。本轮新问题提示还需重点补：满队列 worker 失败竞态、混合 train/eval 状态、semantic-config 往返、masked 非有限项。少量 import 隔离测试可以固定“通用模块不加载 Lightning adapter”的方向；仅检查 `__all__` 不足以证明依赖隔离。

本次 basedpyright 的源码诊断分别在 text evaluator:174、COMET:312、spectral/single:56 和 peft:67/79。其它 15 个位于测试的 mock/narrowing/故意非法参数。不能把历史 readability 文档的“0 errors”视为当前基线。

pyproject 的 core/optional extra 分离总体明确；真实 backend 依赖组合仍应按环境分别验收。当前没有以最小允许依赖版本逐个验证全部 API，报告不声明最低版本矩阵已经通过。

## 建议执行顺序

1. 先分别修复 B1/B2/B3/B4，并消除当前 basedpyright 诊断；行为修复与结构移动分开提交。
2. 下沉 canonical contract primitive 与 audit runtime，保留原公开路径；补 import 隔离验证。这能同时改善 embedding、ADT、quantizer、evaluator 的依赖方向。
3. checkpoint 提取有完整状态所有权的异步 storage；observation 提取 state/schema/serialization 与 snapshot writer。每次只处理一个状态机。
4. 提取 materialization/service 的公共 rank 协调、text/COMET 的 corpus execution、TTS 的 reference materialization。
5. 有后续功能需求时再拆 MoE executor、BiCodec/LongCat、Qwen/CosyVoice adapter、translation 和 s2s integration。

保持现有顶层目录和公开组件组合方式；不把单次审查变成整个仓库的 API 迁移，也不将本轮建议误记为已经完成的重构。
